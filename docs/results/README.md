# Benchmark results

Each folder is one run of `bench/run_m2.sh` (procedure: `bench/README.md`). Every number in these files
sits next to its label (side, where, mode, threads, cap); a number quoted without its labels is not a
result. A run whose parity gates fail publishes nothing, so every folder here passed parity.

## 2026-10-13-500k

ChEMBL 37, 500,000 requested rows (499,997 loaded; 3 failed RDKit canonicalization in the slice builder, 2 more
rejected by the cartridge and excluded from both sides' counts).

This is the corrected run. The first 500k run (tag `milestone-2` before it was moved) had 8 BRICS fragment
queries that matched nothing (radical artifacts), no parity check on `count_substructure`, and a cartridge
consumer path that used 2 parallel workers while labeled threads=1. The fix wave regenerated the queries,
added the count gate, set `max_parallel_workers_per_gather=0`, and reran steps 2 and 5 to 10
(`STEPS="2 5 6 7 8 9 10"`, 19:19 to 22:28). The loads of the first run (steps 3 and 4) passed parity
again and were reused, so the load files and load-phase memory below come from that run.

### What cold means here

- **Cartridge `cold`**: the database container was restarted and `pg_buffercache` showed shared buffers
  nearly empty (196 pages in use before this run; the run refuses above 1%). The Docker VM's page cache
  was **not** dropped, so table and index pages can still come from OS memory. Before the timed repeats,
  each query runs once untimed as `count(*)` (to record hits) and once as the warm-up, so every timed
  sample is at least the third execution. That is why cold and warm cartridge rows are nearly equal.
- **Cartridge `warm`**: `pg_prewarm` of the table and both GiST indexes, then the same procedure.
- **molseal `cold` and `warm` are the same procedure**: a fresh `bench` container loads the snapshot,
  then each query gets one untimed warm-up before the timed repeats. The labels only pair the rows with
  the cartridge's. molseal's real cold cost is `cold_load_s`, the time to load the 169 MB snapshot
  (169,458,886 bytes) into a fresh process: 0.73 s and 0.80 s for the two VM runs, 0.82 s host-native.

### Other notes

- **where**: for molseal, `vm` means the search runs in the `bench` container inside the Docker VM. For the
  cartridge, the search runs in the database container inside the VM, but the Python client sending the
  queries runs on the macOS host through the Docker port forward; the client round trip is in the cartridge
  times. Its size is small: the uncapped id fetch minus `count(*)` for the same query is 0.19 s at p95 (cold and warm).
- **similar** returns ids only on the cartridge side; molseal computes and returns ids with scores.
  **topk100** has no parity gate (the cartridge `<%>` KNN is not compared with molseal's top 100).
- **consumer_path** is single-backend in this run: `bench-cartridge-db-1` stayed at 95-100% CPU in
  `mem_500000.log` during both 5-query windows (19:52-19:56 and 20:22-20:26) and never exceeded 100.6%
  in the whole run. The first run's 13.7 s was a leader plus 2 parallel workers at ~300% CPU.

### Estimate for full ChEMBL (~2.4M rows), not measured

About 4.8x the rows, scaled linearly from the numbers above. Cartridge: relation plus indexes about
5.5 GB, more than `shared_buffers` 4 GB, so the table no longer fits in shared buffers; the container
should sit near 4 GB plus backend memory and peak about 6-7 GB during the GiST builds
(`maintenance_work_mem` 2 GB), and its warm numbers will include page-cache reads. molseal in the VM:
about 5.5 GB RSS, snapshot about 0.8 GB. One side runs at a time, so a 16 GB VM should fit; the planned
24 GB gives margin. This is an estimate until the 2.4M run measures it.
